## 1. 部署环境说明

### 1.1 服务器（game-server 主机，别名 `odoo`）
- 公网 IP：`39.106.99.9`（SSH 别名 `odoo`，需本机 `~/.ssh/config` 配置）
- 应用根：`/opt/game-server`
- 进程管理：systemd 单元 `/etc/systemd/system/game-server.service`
  - `WorkingDirectory=/opt/game-server`
  - `ExecStart=/usr/local/bin/node current/dist/src/main`（原子发布后固定指向 `current` 软链）
  - `NODE_ENV=production`，`Restart=always`，`MemoryMax=500M`，`LimitNOFILE=65536`
- 运行时：`Node ≥ 18`（ESM，路径 `/usr/local/bin/node`）；**服务器内存不足以构建，禁止在服务器执行 `nest build`/`tsc`**
- 依赖服务：PostgreSQL + Redis 以 **docker 容器** 提供（systemd `Wants=docker.service`，先于服务启动）
- 监听：`127.0.0.1:3000`，对外由 nginx 反代

### 1.2 依赖项
- **构建机**：Node ≥ 18、npm、esbuild（前端）、Nest 构建链（后端）、OpenSSH（ssh/scp）、curl（探针）
- **运行依赖**：PostgreSQL（持久化账号/进度/皮肤）、Redis（缓存/队列，按需）、systemd、docker
- **前端**：纯静态，无运行时依赖；构建产出 `bin/`（`index.html`、`bundle.js`、`share.png`、`wechat-share.js`）

### 1.3 网络要求
- 前端域 `game.yourbao.cn` / `game.joho.cn` 必须在 **微信公众平台 JS-SDK 安全域名** 中配置（否则微信内分享/跳转异常）
- `game-server` 的 `CORS_ORIGINS` 必须包含上述两个前端域
- 后端需能 **出站访问** `h.joho.cn/api/zhao-sso`（直验 SSO token、拉取 `/v1/user/me`）
- SSO 回跳 `return_url`/`c_end_url` 必须是前端域名（绝不能指向 SSO 自身），否则 `login.vue` 会拦截

## 2. 完整部署步骤

> 铁律（详见 `game-server/部署协议.md`）：**禁止服务器构建**、**禁止覆盖式部署 `/opt/game-server/dist`**、**`.env*` 永不进包**、**部署后必须双探针自检**。

### 2.1 game-server（后端）

```bash
# ① 本地拉取并安装依赖
git clone <repo> && cd game-server
npm ci

# ② 生成/确认数据库迁移（⚠ 关键：deploy.mjs 不会自动跑迁移！）
#    服务器只部署 dist，没有 src，因此迁移必须从「本地源码 + 可连生产库」执行：
#    方式 A：本地 source checkout 指向生产库后运行
npm run typeorm:run        # 执行 src/migrations 下全部待跑迁移（含本次 0006_refresh_token）
#    方式 B：无直连权限时，用下方等价 SQL 在数据库手动执行（见 §3 附录）
#    新增迁移后务必确认 0006 已落地：SELECT column_name FROM information_schema.columns
#    WHERE table_name='auth_accounts' AND column_name='refresh_token_hash';

# ③ 构建（仅本地）
npm run build              # nest build → dist/

# ④ 原子发布（唯一入口）
node scripts/deploy.mjs    # 构建→本地自检(grep sso-exchange/health)→tar(仅 dist/seeds/指纹)
                           # → scp → 服务器解压到 releases/<ts> → 预检 → symlink 原子切换
                           # → restart → 双探针 → 失败自动回滚上一版
```

- **首次迁移服务器结构**（仅一次）：`node scripts/deploy.mjs init-server` —— 把旧 `dist` 迁移到 `releases/`+`current` 软链、改写 systemd `ExecStart`。
- **演练**（可选）：`--selftest-bad-package`（坏包应被预检拦截）/ `--selftest-bad-runtime`（运行即崩应自动回滚）。
- **双探针预期**：`GET /health` = `200`；`POST /api/client/v1/auth/sso-exchange` = `400`（路由在但参数校验失败）。任一不符 = 未切换/需回滚。

### 2.2 消消乐前端（静态）

```bash
cd xiaoxiaole
npm install
node scripts/build.mjs        # esbuild → bin/bundle.js (IIFE)，并把 .env 配置经 define 注入
# 校验 bin/ 产物：index.html / bundle.js / share.png / wechat-share.js

# 上传到 Web 根（保留上一版备份）
ssh odoo "cp -a /var/www/tour/xxl /var/www/tour/xxl_prev_$(date +%Y%m%d%H%M%S)"   # 路径以实际为准
scp bin/index.html bin/bundle.js bin/share.png bin/wechat-share.js odoo:/var/www/tour/xxl/
```

- nginx 需配置两个入口：`/tour/xxl/`（目录，`index.html` 直接命中 `./bundle.js`）与 `/tour/xxl.html`（alias 返回同一文件，URL 基准为 `/tour/`；首个 404 后 `index.html` 内 `onerror` 兜底加载 `./xxl/bundle.js`）。
- **校验**：浏览器访问 `https://game.yourbao.cn/tour/xxl/` 返回 200，`bundle.js` 200 且为最新构建（可用 E2E 脚本 §4 复验）。

### 2.3 SSO 统一登录中心（strapi + zhao-sso）

- 标准 Strapi 部署（build admin + `node`/`pm2` 启动），详见 `strapi-backend` 仓库。
- **上线前必做**：在 `zhao-sso` 的 `sso_apps` 中注册 `game-xxl`（当前共 9 个应用码），确认登录页路由按 app_code 隔离。
- 后端 `SSO_API_BASE` 指向 `https://h.joho.cn/api/zhao-sso`；前端 `SSO_LOGIN_URL` 指向 `https://h.joho.cn/#/pages/sso/login`。
- 改动 SSO 登录/回调逻辑后，需同步 `login.vue` / `login-callback.vue` 的 hash 参数兜底解析逻辑。

## 3. 关键配置项与参数说明

### 3.1 game-server `.env`（位于 `/opt/game-server/.env`，**不随包，改完 restart**）

| 配置 | 示例 / 默认值 | 说明 |
|---|---|---|
| `NODE_ENV` | `production` | 生产必须 |
| `APP_PORT` | `3000` | 监听端口 |
| `DB_HOST/PORT/USERNAME/PASSWORD/DATABASE` | `localhost:5432` / `game_user` | PostgreSQL；迁移与运行均依赖 |
| `DB_SYNCHRONIZE` | `false` | 生产**必须 false**，靠迁移管理结构 |
| `DB_MIGRATIONS_RUN` | `false` | 本仓不在启动自跑迁移，需手动 `npm run typeorm:run` |
| `REDIS_*` | `localhost:6379` | 缓存/队列；容器提供 |
| `JWT_SECRET` | 强随机串 | **生产必须更换**；与 token 签名绑定 |
| `JWT_EXPIRES_IN` | `7d` | access token 有效期；前端据此设 `expiresAt` 主动续期 |
| `CORS_ORIGINS` | `https://game.yourbao.cn,https://game.joho.cn` | 缺前端域会触发浏览器 CORS 拦截 |
| `SSO_API_BASE` | `https://h.joho.cn/api/zhao-sso` | SSO 直验与 `/v1/user/me` 基址 |
| `ADMIN_DEFAULT_PASSWORD` | 首次登录即改 | 后台管理员 |
| `GAME_*` | 初始金币/钻石/背包/每日任务等 | 玩法数值，按需调整 |

### 3.2 前端注入配置（`.env` → `scripts/build.mjs` 经 esbuild `define` 注入，**运行时不依赖 process**）

| 变量 | 说明 | 缺省行为 |
|---|---|---|
| `GAME_SERVER_API_URL` | 后端外部可达地址 | 空 = 本地模式（云端能力降级，游戏仍可玩） |
| `SSO_LOGIN_URL` | SSO 登录页 | 空 = 内置默认 `h.joho.cn` + `game-xxl` |
| `SSO_APP_CODE` | `game-xxl` | 同上 |
| `SITE_URL` | 站点基址，用于拼分享链接 | 空 = 内置 |
| `MARKETING_API_BASE` | 营销 A/B 接口基址（`https://h.joho.cn`，**非 api.yourbao.cn**） | 空 = 自动跳过 A/B，保持原分享逻辑 |

> 经验坑：营销接口基址曾误填 `api.yourbao.cn`，导致 A/B 分流数据丢失。明确以 `h.joho.cn` 为准。

### 3.3 附录：0006 迁移等价 SQL（无直连权限时手动执行）

```sql
ALTER TABLE auth_accounts
  ADD COLUMN IF NOT EXISTS refresh_token_hash varchar(255) NULL;
CREATE UNIQUE INDEX IF NOT EXISTS idx_auth_accounts_refresh_token_hash
  ON auth_accounts (refresh_token_hash)
  WHERE refresh_token_hash IS NOT NULL;
```
> 回退（down）：`DROP INDEX IF EXISTS idx_auth_accounts_refresh_token_hash; ALTER TABLE auth_accounts DROP COLUMN IF EXISTS refresh_token_hash;`

## 4. 常见问题及排查方案

| 现象 | 根因 | 排查 / 解决 |
|---|---|---|
| SSO 登录 404（sso-exchange 找不到） | 旧包覆盖了 `/opt/game-server/dist`（历史事故：多套构建互相覆盖） | `readlink /opt/game-server/current` 确认指向正确 `releases/<ts>`；`grep -rq sso-exchange /opt/game-server/current/dist/src` 必须命中；否则按 §5 回滚 |
| 双探针 `sso-exchange` 返回 404（非 400） | 部署了不含 sso-exchange 的旧包 | 立即回滚；严禁 `restart` 带病包 |
| 游客/SSO 登录 500（`device_id` 相关） | `auth_accounts.device_id` 列宽 128，长 UA 入库超限 | 迁移列宽至 255（历史 0005/本次钳制）；`login/guest/sso-exchange` 入库前 `slice(0,250)` |
| 浏览器 CORS 报错 | `CORS_ORIGINS` 未含前端域 | 编辑服务器 `.env` 加入 `game.yourbao.cn`/`game.joho.cn`，`systemctl restart game-server` |
| JWT 7 天过期后被强制重新 SSO | 旧版无 refresh token | 本次已补全：后端返回 `refreshToken`+`expiresIn`，前端 `ensureToken()` 临近过期自动 `POST /auth/refresh` 续期；确认 0006 迁移已跑且新前端已部署 |
| 微信内打开邀请链接后跳转异常 | `return_url` 中 `%23`(= `#`) 使 UniApp `onLoad` 参数解析缺失 | `login.vue`/`login-callback.vue` 已有 hash 兜底解析；`debugWx=1` 可强制模拟微信环境验证 |
| 登录后未回跳主菜单 | `return_url` 指向 SSO 自身或缺失 | `login.vue` `onSuccess` 会拦截"目标指向 SSO 自身"；检查前端传入的 `return_url` 是否为前端域 |
| 刷新令牌续期 401 后退出登录 | refresh token 失效/未持久化 | 确认前端 `AuthStore` 已存 `refreshToken`；后端查 `auth_accounts.refresh_token_hash` 是否匹配；封禁账号会抛 `ACCOUNT_BANNED` |

**E2E 回归闸门**（强推荐部署后执行）：
```bash
cd xiaoxiaole && python tools/e2e_sso.py
# 手机视口 390×844 dpr2，测试账号 gametest01；截图交付 design/e2e-sso/
# 通过判据：重定向到 h.joho.cn → 登录 → 回跳 game.yourbao.cn/tour/xxl/ → 主菜单 + 邀请弹窗 → 无 console error → 打印 E2E_OK
```

## 5. 回滚与应急处理

### 5.1 game-server（原子发布，回滚最快）
```bash
# 查看历史版本
ssh odoo "ls -1 /opt/game-server/releases/"
# 回滚到上一版（改软链 + 重启）
ssh odoo "ln -sfn /opt/game-server/releases/<上一ts> /opt/game-server/current && systemctl restart game-server"
# 回滚后必须跑双探针
ssh odoo "curl -s -o /dev/null -w '%{http_code}' http://127.0.0.1:3000/health; \
          curl -s -o /dev/null -w ' %{http_code}' -X POST http://127.0.0.1:3000/api/client/v1/auth/sso-exchange"
# 期待输出：200 400
```
- `releases/` 自动保留最近 5 版，更旧自动清理。
- 数据库迁移一般**不随应用回滚**（结构向下兼容优先）；确需回退用 `migration:revert` 或 §3.3 的 down SQL，且须评估数据影响。

### 5.2 前端（静态）
- 上传前已保留 `xxl_prev_<ts>` 备份；回退即把备份覆盖回 `/var/www/tour/xxl/`。
- 注意 `bundle.js` 文件名固定、带强缓存，回退后建议清 CDN/浏览器缓存或带版本查询串。

### 5.3 应急通则
- **改环境变量** = 直接编辑服务器 `.env` + `systemctl restart game-server`，**不要**重新发包。
- **严禁**在服务器 `npm ci` 之外执行构建、严禁解压到 `dist`、严禁把 `.env` 打进 tar。
- 线上事故先恢复服务（回滚/重启），再定位根因；所有部署在 `部署协议.md` 的「部署记录」表追加一行（时间/操作者/版本/自检结果）。

## 6. 开发经验总结（独立章节）

### 6.1 技术选型与架构决策
- **统一 SSO 中心而非各游戏各接微信 OAuth**：采用对齐 `nshop` / `vendure cjk-plugin` 的「对齐方法」——用 SSO `/v1/user/me` 的 `uuid`（唯一键）与 `sso_user_id`（数字 id）对齐本地账号，登录即换发本站 JWT。好处：一套登录、一套分销/邀请关系、微信生态统一；代价是前端需整页跳转（无法纯 API 静默登录）。
- **token 直验**：后端用 SSO `access_token` 直接调 `/v1/auth/validate-token` + `/v1/user/me`，不依赖 OAuth `state` 解码兜底，降低状态错乱风险。
- **游客认领（claimAccountId）**：未登录玩家先以设备建游客账号，SSO 登录后把旧进度/积分/皮肤认领到 SSO 用户名下，避免进度丢失——这是留存关键设计。
- **前端单包 + 构建期注入配置**：esbuild 打 IIFE 单包、用 `define` 把 `.env` 顶替为常量，运行时不依赖 `process.env`，既减小体积又规避浏览器全局污染。
- **统一响应包裹 `{code,msg,data}` + DTO 校验**：前端 `AuthStore` 只认 `env.code===0`，后端 `ResponseInterceptor` 统一包装，错误码集中管理。

### 6.2 典型问题及解决方案
1. **多套构建互相覆盖 `dist`（最严重事故）**：消消乐 SSO 构建与旧全量构建（含其他模块、无 `sso-exchange`）三次互相覆盖，导致全部游戏 SSO 404。→ 立 `部署协议.md` 铁律 + `deploy.mjs` 原子发布（`releases/`+`current` 软链 + 双探针 + 自动回滚），从机制上根除。
2. **长 UA 触发 `device_id` 列宽 500**：`CREATE`/`UPDATE` 时超长 `user-agent` 入库报 500。→ 列宽 128→255 + 入库前 `slice(0,250)` 钳制（双保险）。
3. **刷新续期缺失（本次补全）**：原 `authedFetch` 已写 401 自动刷新逻辑，但后端从不返回 `refreshToken`、也无 `/auth/refresh`，JWT 7 天过期即强制重登。→ 新增 `refresh_token_hash` 列、登录/换会话返回 `refreshToken`+`expiresIn`、`refresh()` 轮换令牌。
4. **hash 路由模式参数丢失**：UniApp H5 hash 模式下 `return_url` 含 `%23` 使 `onLoad` 解析缺参。→ `login.vue`/`login-callback.vue` 增加直接从 `window.location.hash` 兜底解析。
5. **微信环境自动跳转 + 埋点去重**：`debugWx=1` 模拟微信；`invite-view` 埋点按 `sessionStorage` 每会话每码去重，失败静默不影响登录。

### 6.3 性能优化与代码规范实践
- **后端**：Nest 模块化按 `app_code` 隔离；迁移采用 `000x_*` 顺序命名并保留 up/down；纯函数（`checkDist`/`depsHash`）配 `node --test` TDD，保证部署自检可靠。
- **前端**：`bundle.js` 单文件 IIFE、生产 `minify` + 开发 `sourcemap`；`AuthStore` 集中管理 token/refresh/过期判定，避免散落；`authedFetch` 统一拦截 401→刷新→重试。
- **配置零运行时依赖**：构建期 `define` 注入，避免浏览器端 `process` 不可用问题，也方便多环境（yourbao/joho）复用同一份源码。
- **可观测**：`recordLoginLog` 记录登录成败；前端 E2E 真机脚本用真实账号做回归闸门，比纯单元更能发现跨域/跳转链路问题。

### 6.4 团队协作与流程改进建议
- **部署协议前置**：任何线上操作前必读 `部署协议.md`，把"禁止服务器构建/覆盖式部署/.env 不进包/双探针/唯一入口"写成铁律并落到自动化脚本（`deploy.mjs`），用工具而非人脑兜底。
- **部署记录审计表**：每次部署在协议文档追加（时间/操作者/版本/自检结果），形成可追溯的事故/变更时间线。
- **E2E 作为发布闸门**：把 `tools/e2e_sso.py` 接入发布流程，未过 E2E 不准视为发布完成。
- **经验沉淀进 memory / 文档**：如"营销接口基址填 `h.joho.cn` 而非 `api.yourbao.cn`"这类易错点，写入可检索的笔记，避免重复踩坑。
- **迁移与发布解耦**：认清"deploy.mjs 不打迁移、服务器无 src"，把迁移明确为发布前独立步骤（本地跑 `typeorm:run` 或手工 SQL），并在交接书中单列，防止"代码上了但表没改"的线上故障。
