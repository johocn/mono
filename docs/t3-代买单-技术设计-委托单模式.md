# t3 代买单（委托单模式）详细技术设计

> 版本：v1.0（2026-10-18） · 对标：美团买单 · 定稿版式：A 委托单模式
> 关联底座：vendure coupon-plugin / merchant_settlement_ledger / nshop storefrontMode

---

## 1. 定位与合规定性

- **业务定位**：t3 租户（channel code `t3`）=「代买单」服务租户。客户提交买单委托（商家、预计金额、备注）→ 平台按规则报价（含优惠）→ 客户在线支付 → 管家以 t3 名义向商家完成支付 → 凭证回传 → 台账结算。
- **合规定性（关键）**：t3 与客户之间是**委托服务合同**，客户支付的是「代买单服务对价」，收款进 t3 微信商户号合法（自有服务收入，非代收代付）。**红线**：用户资金先进 t3 再「代收代付式」转结商家 = 二清（银办发〔2017〕217号 / 《非银行支付机构监督管理条例》§47），商业模式必须按「差价模型」设计（见 §6）。
- **盈利模型**：客户费率（如 90%）− 商家协议费率（如 85%）= 毛利费率，按单入台账。P1 叠加 t1 券联动与会员费增厚。

## 2. 数据模型（新包 `bill-pay-plugin`）

### 2.1 `BillPayOrder` 实体

### 2.2 `merchant_agreement` 商家协议表（P0 轻量）

| 字段 | 说明 |
|---|---|
| `channelId` / `merchantName` | 渠道内按商家名唯一 |
| `settleRate` | 协议结算费率（百分数整数，85 = 8.5 折） |

## 3. 状态机

```
PENDING_QUOTE → QUOTED → PAID → IN_SERVICE → COMPLETED → SETTLED
   ↓(客户取消)    ↓(客户取消)
CANCELLED      CANCELLED
          PAID ──(未接单退款)──→ REFUNDED
```

| 状态 | 触发 | 动作 |
|---|---|---|
| `PENDING_QUOTE` | 客户提交 | `autoQuote=true` 时同步报价，瞬时转 `QUOTED`；否则等管家改价 |
| `QUOTED` | 报价完成 | 客户可见应付；超 `quoteExpireAt` 自动失效回 `PENDING_QUOTE` |
| `PAID` | 微信回调/余额支付 | 原子置 PAID（参照 coupon-sale 回调幂等实现） |
| `IN_SERVICE` | 管家接单（web-admin） | 记录 `operatorId`；此后取消/退款仅人工 |
| `COMPLETED` | 凭证回传 | 填 `actualAmount` + `proofUrl`；实际金额超出容忍阈值（默认报价 ±10%，可配）需备注说明 |
| `SETTLED` | 财务结算 | 写 `merchant_settlement_ledger` 台账行（类型 `BILLPAY_SERVICE`），毛利 = quote − actual×settleRate 对齐差价模型 |
| `CANCELLED` | 客户自助 | 仅 `PENDING_QUOTE`/`QUOTED` 可自助取消 |
| `REFUNDED` | 微信原路退 | 仅 `PAID` 且未接单；IN_SERVICE 后走人工退款入口 |

## 4. 优惠报价引擎（纯函数，不走 Vendure 促销引擎）

促销引擎绑定购物车行，不适配任意金额单，故独立实现纯函数（对齐项目 detail-config 的「坏配置返回 null 逐级回退」模式）：

```ts
// bill-pay-plugin/src/quote-engine.ts
export interface BillPayRule {
  memberDiscount?: { percent: number; label: LocalizedText }; // 90 = 9折
  thresholds?: { minSpend: number; reduce: number; label: LocalizedText }[];
  minAmount: number;  // 分，低于此金额不接单
  maxAmount: number;  // 分，超出转人工
}
// 输入分单位整数，输出 { payable, discountDetail }；叠加顺序：会员折扣 → 最优满减档
export function quoteBill(expectedAmount: number, rule: BillPayRule): QuoteResult
```

规则来源：`channel.customFields.billPayConfig`（JSON，参照 orderListConfig 模式）：

```json
{
  "autoQuote": true,
  "quoteExpireMinutes": 30,
  "memberDiscount": { "percent": 90, "label": { "zh-CN": "会员9折", "en-US": "Member 10% off" } },
  "thresholds": [ { "minSpend": 10000, "reduce": 500, "label": { "zh-CN": "满100减5", "en-US": "¥5 off over ¥100" } } ],
  "couponEnabled": false,
  "tolerancePercent": 10,
  "minAmount": 2000,
  "maxAmount": 200000
}
```

- 全程分单位整数运算；解析函数 SSR 友好、坏 JSON/缺字段回退默认。
- 券抵扣位（`couponEnabled`）P0 预留不实现，P1 接 t1 付费券。

## 5. 支付链路（复用 + 改造）

1. `createWechatBillPayment(id)`：取 `quoteAmount`，生成 `BP-*` 外部单号，默认 JSAPI，调用本插件内的 bare 支付实现（**P0 复制 coupon-sale.service.ts L174-205 的模式，不抽取共用模块、不改动 coupon-plugin 任何文件**，杜绝 t1 回归风险；稳定后再评估共用抽取），记录 `paymentMethod='wechatpay'`。
2. 微信回调：按 `BP-*` 前缀路由到 bill-pay 回调处理器，**原子**置 `QUOTED → PAID`（幂等，参照 coupon-sale L208-237）。
3. 余额支付（可选）：`payBillPayOrderWithBalance` 先置 PAID 再扣余额（同 L152-170；P0 不新增充值入口，仅消费既有余额，规避预付卡问题）。
4. 退款：`PAID` 未接单场景调微信原路退款，置 `REFUNDED`。

## 10. 资金与结算

1. 收款：客户支付 `quoteAmount` 进 t3 微信商户号（服务收入）。
2. 代付：管家现付商家 `actualAmount`（`PER_ORDER`；商家按协议价收款——即商家给 t3 的协议折扣在收款时体现）。
3. 台账：`SETTLED` 时写 `merchant_settlement_ledger`，记录 quote/actual/settleRate/毛利，月度对账出报表。
4. 差异处理：`actualAmount` 超出报价容忍阈值（默认 ±10%）时 COMPLETED 需备注，差额走人工客服（补差/退差）。
5. 护栏：不提供 t3→商家自助资金转移界面；商家结算对公/月结留痕；发票按服务费口径由 t3 开具。

## 13. 合规论证与手续清单（2026-10-18 补充）

**定性**：客户↔t3 为委托服务合同（客户付款是 t3 自有服务收入，非代收货款）；t3↔商家为普通买卖合同（t3 以买方身份消费）。不触碰「平台留存商户结算资金并自行清算」的二清认定核心。类比跑腿代购合规先例：明示代办身份、不冒用商家名义、不经手食品制作。

**破防条件（必须规避）**：① 向商家宣传「收款/结算」服务；② 商家挂账、平台月度代收再结算；③ 充值余额池（资金沉淀）；④ 买单后退现金（套现通道）。

**手续清单**：营业执照（经营范围含生活服务/代办服务）→ t3 主体微信商户号（类目=生活服务/跑腿代办，勿选餐饮零售）→《委托服务协议》+ 隐私政策（前端强制勾选）→ 发票口径（t3 开服务费发票给客户、商家开成本票给 t3，客户无商家原始发票须产品明示）→ 差价收入税务（增值税+所得税）→ 套现风控制度（单笔+单日限额、强制凭证、高频/整数金额拦截、退款只原路、备用金台账）→ 优惠宣传真实性（禁虚构已售）→ 建议律师出具《业务模式合规意见书》。

**设计侧需补三处**：提交页协议勾选、`billPayConfig` 增加单日限额字段、页面固定「代买代办」身份声明文案。

> 本节为业务分析，不构成法律意见；上线前应经执业律师审核。

## 15. 业务隔离护栏（硬约束：不破坏其他业务流程）

原则：**纯增量**——新增文件/新增表/新增接口，不改既有表结构与既有接口行为。逐项护栏：

| 触点 | 护栏 |
|---|---|
| 数据库 | 迁移只建新表（bill_pay_order / merchant_agreement），禁止 ALTER 既有表；ledger 若需新类型值用枚举追加（向后兼容，先确认所有 ledger 消费方按类型过滤汇总，避免报表把 BILLPAY_SERVICE 算进商家应付） |
| coupon-plugin | P0 零改动（支付实现复制不共享）；任何共用抽取推迟到 P1 并单独立项回归 |
| 微信回调 | 在回调分发处增加 `BP-*` 精确前缀分支，CS-\*/既有分支与默认兜底逻辑不动；单测覆盖同一回调入口两单号互不串扰 |
| 渠道隔离 | BillPayOrder/商家协议查询一律带 `channelId`（继承既有租户数据隔离）；t3 之外的渠道 shop-api 查询恒返回空 |
| storefrontMode | `useStorefrontMode` 增加 billpay 分支为增量：未知值/无配置回退现有行为；t1 `coupon`、普通模式渲染路径零改动；买单入口仅渲染于 `storefrontMode==='billpay'` 渠道 |
| 订单中心 | BillPayOrder 不是 Vendure Order，不进任何既有订单列表（t1/t2 订单页零变化）；买单委托单入口独立，仅 t3 渠道显示 |
| 促销引擎 | 不触碰（报价为独立纯函数），既有购物车促销行为不变 |
| 余额体系 | 只消费既有余额，不新增充值入口 |
| GraphQL | 仅新增 type/mutation/query，不改既有字段语义；admin 新权限 `BillPayManage` 不影响既有角色默认能力 |
| web-admin | 新增菜单/页面/权限项，既有页面不改动；部署走既有 deploy.mjs |
| nshop 构建 | 构建影响全租户 → 发版后按 §11 回归清单对 t1/t2/普通渠道做既有冒烟；买单相关 chunk 仅在 t3 入口加载 |

验收口径：以上护栏逐条写入 P0 的 e2e/回归用例，任一护栏失败即阻塞发版。
